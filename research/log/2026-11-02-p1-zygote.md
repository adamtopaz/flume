# p1-zygote: compile modules in forked children of one pre-initialized Lean process (P1)

- **Date:** 2026-11-02
- **Author:** Claude (Opus 5.5), owner loop, machine `2e698309` (i9-14900K, 16 of 32 CPUs, 32 GB cap)
- **Milestone:** P1 (no `lean` start-up per module)
- **Outcome:** success
- **Branch / PR:** research/p1-zygote: https://github.com/adamtopaz/flume/pull/6
- **Result files:** research/results/20261103T004822Z-2e698309-b0d74fa.json

## Plan

Every compile flume runs is a fresh `lean` process that `exec`s, links `libleanshared`,
and runs Lean's initialization before reading its file: `lean --version` takes 21-24 ms on
this machine. That is paid once per module in `cold` and `hub-interface` (1,000 modules,
~0.74 CPU-s each, so ~3%) and on every step of a chain in `swarm`. Blake's `fork-lean` and
`one-zygote` iterations (github.com/adamtopaz/blake, `research/ideas/one-zygote.md`) did
the same for Lake with byte-identical artifacts on this toolchain and gained 5-7% on
`swarm` and `hub` and ~5% on `cold`.

The plan follows Blake's design, adapted to flume:

- **The zygote** (`crates/flume/src/zygote.c`, from Blake's `c/blake_zygote.c`, same author
  and license): a single-threaded C program linked against the toolchain's
  `libleanshared`. It calls `lean_initialize()` once, prints `ready`, and then forks one
  child per request; each child redirects its output to files, sets `LEAN_PATH`, and runs
  the steps of `lean_main` (v4.35.0 `src/util/shell.cpp`) that follow initialization,
  ending in `lean_shell_main`: `lean`'s own driver, so the same artifacts.
- **Building it without a build script** (`build.rs` is not allowed): flume embeds the C
  source and compiles it on first use with `cc` (no machine-specific flags) into its cache
  directory, keyed by the source and the toolchain; without a C compiler, or for a
  toolchain other than the one the C mirrors, flume runs `lean` as before.
- **Using it without slowing single compiles:** the zygote starts in the background at the
  first compile of a build; compiles go to it only once it has printed `ready` and run
  `lean` directly until then, so a build with one compile (leaf, newfile, hub-private) pays
  nothing but a process started on another core. At the end of the build every request has
  been answered, so the zygote has no children and is killed and reaped: nothing outlives
  the command. The worker pool still bounds concurrent compiles (each worker waits for its
  own reply).
- The child's search path: the zygote's built-in path is relative to its own location, so
  the toolchain's `lib/lean` (which `lean` appends last) is appended to `LEAN_PATH`.

Targets: `leaf, newfile, hub-interface, swarm, cold` (P1's). I expect hub-interface and
swarm to improve by a few percent and cold slightly (under its 7% threshold), and the
single-compile scenarios to stay put. Measured with `--repeat 5 --repeat-fast 20` from the
start (`2026-11-02-p2-local-cache-2.md`: this machine's noise produces false regressions at
3/10).

## What was done

- `crates/flume/src/zygote.c` (new, from Blake's `c/blake_zygote.c`): the fork server,
  with a `ready` line after initialization, `PR_SET_PDEATHSIG` in each child (a child never
  outlives the zygote, so a fallback compile cannot race one), and a child path re-checked
  against v4.35.0's `lean_main` (`~/.cache/blake/lean4-src`, tag v4.35.0). Blake's version
  differed from `lean` in ways the benchmark never exercises, now fixed:
  - `lean` runs `lean_shell_main` on a thread with the configured stack size (1 GB by
    default on 64-bit, or `LEAN_STACK_SIZE_KB`), Blake's on a fixed 64 MB thread; a deep
    recursion that `lean` survives could have crashed the child. The child now reads
    `LEAN_STACK_SIZE_KB` as `set_thread_stack_size_from_env` does and runs the driver
    through `lean_run_main` (the exported `run_with_thread_stack`);
  - an IO error from `lean_shell_main` is printed to stderr before exiting 1, as `lean`'s
    `catch` does, and a failing search-path setup prints `error: ...`;
  - option parsing stops after `--run`, the task manager is finalized after the driver
    (`scoped_task_manager`), and the externs have v4.35.0's signatures (no world token).
- `crates/flume/src/zygote.rs` (new): building it (`cc -O2` against the toolchain's
  `include/` and `lib/lean/libleanshared`, atomically into
  `<cache>/zygote/<hash of source, prefix, version>/`, a `failed` marker if `cc` fails),
  starting it on a background thread at the first compile, the request/reply protocol (each
  worker registers a channel, writes its request, waits for its exit code; a reader thread
  delivers replies), stdout/stderr through files in `.lake/flume/zygote/`, and `finish`
  (kill, reap, join) at the end of every build.
- `crates/flume/src/build.rs`: `compile` builds `lean`'s argument list once and asks the
  zygote first; it falls back to `lean` (after clearing outputs again) when the zygote is
  not ready, unavailable, or died, and also for libraries whose `weakLeanArgs` and
  `moreLeanArgs` are not all `-D` options (`--tstack`, `--profile`, `--run` are where the
  zygote cannot match `lean` exactly). `-v` marks compiles done by the zygote.
  `FLUME_ZYGOTE=off` disables it.
- `tests/check_zygote.py` (new): a package with a warning, an error, a blocked dependent
  and an ordinary (non-module) file, built with and without the zygote: same exit status,
  same messages, same failed modules, 31 byte-identical artifacts, at least 3
  compiles done by the zygote, no process left. `research/DESIGN.md` updated.

Checks: `cargo build/test/clippy/fmt` clean, `tests/check_cache.py` and
`tests/check_zygote.py` ok, quick suite (lake, main, candidate) and the held-out quick suite
both `identical artifacts to lake, all builds ok, break check ok`. On the quick suite
(1-2 runs, not decisive) `hub-interface` was 1.05-1.13x faster than `main` and `cold`
1.02-1.11x.

No scenario regressed. Also `improved`, but not by anything this change does: `clone`
on three corpora (1.08x; no compile runs there, so the zygote never starts) and
medium-deep/agents-4 (1.049x), medium-legacy/noop (1.083x), medium-layered/newfile (a
single compile, which runs `lean` directly). These are the noise this machine produces
(see `2026-11-02-p2-local-cache-2.md`); the scenarios the zygote serves are the ones that
improved consistently.

CPU time (user + system) per build, `main` / candidate: `hub-interface` 641 / 603 s
(deep), 687 / 646 s (layered), 642 / 612 s (legacy), 634 / 589 s (wide), i.e. 30-45 CPU-s
less per ~900 compiles, about 40-45 ms per compile (more than `lean --version`'s 22 ms on
an idle machine: start-up under load also pays for page faults and dynamic linking on
busy cores); `cold` 677 / 637, 792 / 735, 738 / 732, 647 / 600 s. Peak memory of the
build's scope (first run of each) was 1-10% lower with the zygote in 9 of the 11 cold,
hub-interface, and swarm builds (one shared initialized image instead of one per
process) and 1-4% higher in the other two (layered/swarm, legacy/cold).

`medium-legacy/cold` (0.979x, within its 7% threshold) is the one corpus whose cold builds
ran candidate first; it is also the only first build of the candidate's cache, so it
compiled the zygote (`cc`, ~0.7 s on a background thread) and the early waves of modules
ran `lean` directly. The other cold builds improved 6.8-10.7%.

## Conclusion

- **P1 is done.** Compiles after a build's first ones run in forked children of one
  initialized Lean, `lean`'s own driver on the same arguments, and the harness found the
  artifacts identical to Lake's after every build on every corpus (and the held-out
  corpora). `hub-interface` is 6.5-9.5% faster than `main` on every corpus, `swarm` 3.7-6.5%
  on the two chain-bound corpora, `cold` 5.5% on average; builds with one compile are
  unchanged, as designed.
- **What is left of start-up:** the first wave of a build still pays `lean`'s start-up
  (it runs while the zygote initializes), and single-compile builds (leaf, newfile,
  hub-private) gain nothing: their remaining time is the compile itself plus the imports.
  A build server (P3) could keep a zygote warm across builds, which would make the leaf
  edit's compile skip start-up too; environment reuse (P4) is the next large lever for
  every scenario that compiles (Blake measured imports at ~35-40% of a deep module).
- **Watch for:** the zygote mirrors v4.35.0's `lean_main`; a toolchain bump must re-check
  `src/util/shell.cpp` and update `LEAN_VERSION` in `zygote.rs` (another release silently
  runs `lean` directly, so nothing breaks, it just stops being faster). A machine without
  `cc` also runs `lean` directly; CI's runner has `cc`, so the quick suite in CI exercises
  the zygote.
