- **Result files:** none committed (the baseline follows in a `log:` PR measured with the merged harness)

## Plan

Start flume as a minimal build system for Lean 4 that is exactly as correct as Lake from
its first commit, so every later iteration can be judged by speed alone: a Rust driver
that mirrors Lake 5's compilation of a module and its rebuild rules, a small Lean worker
for what needs Lean, the phase-2 benchmark developed for Blake (module-system corpora,
five edit kinds, many-checkouts scenarios, sizes up to 100,000 modules), CI, and this loop.

## What was done

- **Driver** (`crates/flume`): reads `lakefile.toml` libraries; parses headers with a
  port of Lean's `ParseImportsFast` (agrees with Lean on all 2,546 files of the
  toolchain's sources, `tests/check_headers.py`); keys modules with Lake's exact traces
  (`addImport`, `computeExportInfo`); writes Lake's setup files (`fetchTransImportArts`
  walk) and runs `lean` with Lake's arguments; removes old outputs before compiling as
  Lake does; remembers source status and imports so a no-op build reads nothing;
  verifies outputs by content when their file status changes (copied checkouts).
- **Worker** (`worker/`): exposes Lean's own header parser (`flume-worker headers`).
- **Benchmark** (`bench/`): ported from Blake's local `bench/phase2-scaffold` branch, with
  flume and Blake as tools; the harness now waits for systemd to notice an emptied scope
  (flume's no-op build finished before systemd did, which read as a straggler).

Rebuild decisions were checked against stock Lake by hand on 200-module corpora (both
module-system and ordinary files): every edit kind on the leaf and the hub, a swarm
edit, a new file, both breaking edits and their recovery. flume rebuilt exactly the
modules Lake rebuilt in every case, the artifacts were identical after every build
(1,400 and 600 files), and even the broken state matched once old outputs were removed
before compiling.

An independent review of the first version found, and reproduced against stock Lake,
cases the benchmark never exercises; all were fixed before merging:
- deleted outputs other than the `.olean` went unnoticed (every output is now checked by
  status, then content); the harness gained a repair step that deletes artifacts;
- a header that could not be read or parsed, an unknown import, or an import cycle
  aborted the whole build (now only that module fails and its dependents are blocked;
  unknown imports are left to `lean`, as Lake does);
- `weakLeanArgs` came after `moreLeanArgs` on the command line (artifacts could differ)
  and were part of the key (needless rebuilds); sources were hashed without normalizing
  line endings (needless rebuilds after a CRLF conversion);
- imports resolved to the first library instead of Lake's last buildable one; globs with
  missing bases, missing directories, or symlinked directories, and an empty default
  target list, behaved differently from Lake;
- options such as `buildType = "debug"` were silently ignored (unknown and unsupported
  options are now errors);
- process holes: `.gitignore` hid `research/results/`, the PR check ran the PR's own
  rules, untracked files did not make a tree dirty, and the harness's variables reached
  the measured tool.

Every case was rerun against stock Lake afterwards: the same modules were built, with the
same exit status and identical artifacts, in all of them. Only the wording and the number
of `✖` lines for header-level failures differ (Lake reports them as separate jobs).

## Measurements

Quick suite (small corpora, not a standard run), stock Lake vs flume v0:

```
speedup of candidate vs lake: cold=1.030x, noop=4.706x, leaf=1.502x, newfile=1.734x, hub-private=1.315x, hub-interface=1.043x, swarm=1.086x, clone=0.016x, agents-4=1.107x, workflow:single=1.623x, workflow:many=0.131x, workflow:cold=1.030x, overall=0.603x
correctness of candidate: identical artifacts to lake, all builds ok, break check ok
```

Outside the harness (no systemd scope per build), a no-op build of 200 modules takes
about 4 ms with flume against about 130 ms with Lake.

## Conclusion

- flume v0 is correct on every scenario and corpus of the benchmark and already faster
  than Lake wherever Lake's own overhead matters (no-op, leaf, new file, hub edits that
  keep the interface).
- `clone` is the gap: Lake restores a fresh checkout from its artifact cache in ~0.15 s,
  flume rebuilds it from scratch. Roadmap P2 (shared content-addressed cache) closes it,
  and that dominates the many-checkouts workflow and the overall number.
- Heavy scenarios (`hub-interface`, `cold`, `swarm`) are bound by `lean` itself; P1 (no
  start-up per module) and P4 (environment reuse) are the levers there.
